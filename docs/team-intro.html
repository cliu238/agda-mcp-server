How This Fork's Self-Improvement Loop Works

This page explains the self-improvement loop, the team feedback channel that feeds it, and how to tell whether you need the plain-user path or the team-member path for this fork.

↻ RE-USE loops back into USE: the hardened server is what the next proof session runs against, so the cycle compounds instead of resetting.

JUDGE is not a single check. It runs the oracle triad — three separate predicates, not one cold re-run — and a warm-replay anti-phantom gate sits between JUDGE and FILE so a flaky, non-deterministic result never gets mistaken for a real, reproducible defect. See "The loop, stage by stage" below for the full detail.

The loop, stage by stage

Core value: "every real proof session reliably converts into a stronger server."

1. USE

An AI agent — Codex or Claude Code — does real Agda proof work through the MCP server. The session runs via the dogfood proxy (scripts/dogfood/dogfood-run.mjs), which records the session as it happens rather than requiring anyone to reconstruct it after the fact.

2. SURFACE

Somewhere in that real session, a defect or gap shows up: a crash, a wrong result returned by a tool, or — the trickiest case — a suspicious "green," where the server reports success but something about the outcome doesn't actually add up. Loop 2 treats all three as first-class signals worth capturing, not just hard crashes.

3. CAPTURE

Once something surfaces, capture is near-one-click: the agda_capture_session tool builds a self-replaying capture artifact plus a replay manifest. Every capture carries stable fingerprints so the same underlying defect, seen twice, gets deduplicated instead of filed as two separate issues.

4. JUDGE

This is where Loop 2 differs sharply from a naive "just re-run it" approach. A single cold re-run is not enough, because different false-green failure families require different detection strategies — a defect that a cold re-run would catch is not the same shape of defect as an agent quietly narrowing scope to make a proof "pass." Each false-green family needs its own predicate, so JUDGE runs three of them together as the oracle triad:

The oracle triad — three predicates, not one:

  • ORCL-01 (cold-rerun differential): a fresh compile in a clean environment, so environment-dependent flukes (stale caches, leftover state) can't masquerade as a real pass.
  • ORCL-02 (soundness scan): detects agent cheats specifically — sneaky postulates slipped in to fake a proof, flag-planting, or scope narrowing that quietly changes what's actually being proved.
  • ORCL-03 (conformance proxy): checks whether the proved statement actually matches what was asked in the first place, using the expectedSignature captured up front at session start — so a technically-valid proof of the wrong statement doesn't count as a win.

None of these three predicates is redundant with the others: a cold re-run alone would miss a sneaky postulate that still typechecks cleanly on a second run, and a soundness scan alone wouldn't catch a proof of the wrong theorem. All three run together before a "success" is trusted.

On top of the triad, an N-times warm-replay anti-phantom gate runs before anything reaches the fix queue: if a result is flaky under repeated replay rather than deterministically reproducible, it is routed to a side channel instead of being filed as a defect, so timing flakes never pollute the fix queue as if they were real, fixable bugs.

The design of this whole JUDGE stage is grounded in observed real agent behavior, not hypothetical failure modes: during the team's autoformalization campaigns on two pinned fuel corpora — codex-homotopy-group and autoformalizing-hopf — agents were observed narrowing scope, taking shortcuts, and planting flags specifically to look done. The oracle triad exists because those behaviors were seen for real, not imagined in the abstract.

(One north-star, deliberately deferred idea sometimes mentioned alongside this loop is "Loop 1" — turn-based proof guidance from the server itself, e.g. "you have 3 goals, suggested next: case-split on n." It is out of scope here; it's only worth recognizing the name if you see it elsewhere.)

5. FILE

Judged, non-flaky defects land in a zod-validated flat-file fix queue, with priority ordering and fingerprint-based deduplication so the same underlying bug is never filed twice under different names. The current state of the queue is visible at docs/FIX-QUEUE-DASHBOARD.md. As of the v1.1 close, the queue held 18 entries: 10 locked, 7 triaged, and 1 rejected.

6. FIX+LOCK

Each fix in the queue lands with a from-RED regression test: the test is written first, against the bug, and proven red (failing) before any fix code is written — only then does the fix turn it green. This ordering is deliberate: the loop never golden-masters a false-green, meaning it never writes a test that just encodes the buggy behavior as if it were correct. A regression test always represents the intended, correct behavior, not whatever the server happened to do before the fix.

7. RE-USE

The hardened server — with the new regression test locked in — goes back into the next real proof session. That closes the loop: RE-USE is USE again, but against a strictly stronger server than before. Each cycle compounds, so the server that today's session runs against is never weaker than the one from any prior session.

This loop is not a hypothetical design exercise — it has a real, end-to-end track record. v1.1 shipped 4 phases, 24 plans, and 17 out of 17 requirements. A live Codex session on the pinned corpus surfaced a real defect, fingerprint 0bc76d15c2fec8df, which went capture → judge → file → fix → lock end-to-end with zero fixture shortcuts. That single run — known internally as E2E-01 — is the strongest evidence that this loop works for real sessions, not just curated demo cases.

The team feedback channel

The team feedback channel exists so that teammates' real proof sessions become loop fuel without the maintainer needing to be in the room for every session. It is the mechanism that lets Loop 2 scale beyond the maintainer's own dogfooding.

Local side: from key to upload

The pipeline starts with the maintainer issuing a revocable Bearer key out of band, using scripts/team/issue-key.mjs. The server's registry stores only key hashes, never the raw key value, and a consent statement is shared alongside the key so the teammate knows exactly what an upload will contain before they start.

From there, the teammate does their proof work through the dogfood proxy exactly as in the core loop, which records the session as it happens. When the session wraps up, dogfood-wrapup.mjs runs the same oracle-triad judging described above, but locally, on the teammate's own machine — judging is not deferred entirely to the cluster. Finally, upload-run.mjs uploads the resulting run archive. This upload step is deliberately fail-open with a bounded local retry queue: if the ingest endpoint is unreachable, the upload never blocks or corrupts the teammate's proof work — it just queues locally and retries later.

Cluster side: ingest, judge, and feed the fix queue

The ingest endpoint, https://dev.sites.idies.jhu.edu/agda-mcp/ingest, runs on the JHU IDIES k8s cluster. It receives each upload streamed with a 512 MiB cap, and archives it by person and date onto durable Ceph PVC storage. A health check is available at https://dev.sites.idies.jhu.edu/agda-mcp/healthz.

A daily sandboxed cron job on the cluster, cron-ingest-wrapup.mjs, re-judges each day's uploads and files any findings into the same fix queue described in the core loop above. Fixes discovered this way get locked with regression tests exactly like any other fix, and teammates pick up the hardened server simply by checking out the next v* tag. Notably, the cluster runs the exact same scripts as local — the only differences are configuration, not logic — and main auto-deploys to the cluster on every push, so the deployed judge is never stale relative to the repo.

Privacy and consent, in plain terms:

Upload keys are revocable and stored only as hashes, never as raw values. The consent statement shared with each key tells the teammate exactly what an upload contains before they opt in. Uploads are archived per-person, not pooled anonymously. No credential of any kind lives in this repository — keys are issued and revoked entirely out of band by the maintainer.

Two ways to be here

Not everyone using this server needs to join the team feedback channel. The table below lays out the two paths side by side.

The key framing to hold onto: the plain path is a strict subset of the team path. Team membership adds reproducibility pinning plus the upload channel on top of the plain path; it does not change how the server itself works underneath you.

Your own project's proof sessions are first-class fuel for this loop, not a fallback: agda_capture_session inlines your project's own first-party source files into the capture, so the judge can replay the session on another machine without your original checkout (design decision D-07) — as long as your project's library dependencies are among the pinned public libraries (agda-stdlib, agda-unimath). The pinned corpora exist as shared library dependencies and as the research team's own work sites, not as the only proving ground the loop accepts sessions from.

Which one am I? If you are just using the server on your own Agda project, you are a plain user and README.md is all you need. If you want your proof sessions to harden the server for everyone — and are willing to install the pinned environment and get an upload key from the maintainer — follow docs/TEAM-ONBOARDING.md instead.
