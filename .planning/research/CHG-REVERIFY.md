## Defect 1: False-green verdict family (#64/#61 flagship)

**Verdict:** changed

**v0.6.7 claim:** Per `.planning/STATE.md` and `.planning/research/ORACLE-VALIDITY.md`: on 2026-05-30, CHG (Codex-Homotopy-Group, agda-mcp-server v0.6.7, Agda 2.8.0) injected a real type error and found `agda_load` / `agda_typecheck` / `agda_load_no_metas` / `agda_proof_status` **ALL** returned `ok-complete` / zero errors while raw `agda` rejected with `UnequalTerms: UU !=< A`. `.planning/codebase/CONCERNS.md` names the architectural root cause as GitHub #64 ("stale transitively-imported dependency interfaces" — `forceRecompile` only busts the *named* file's own `.agdai`, not its transitive dependencies') and #61 (a related unescalated-error/stale-cache class), and separately (01-CONTEXT.md deferred list) flags "state-change tools reporting 'solved' after a failed reload" as its own candidate defect — which turned out to be directly observable in this repro's `agda_proof_status` output (see below).

**Repro:** Three independent repro shapes were run, all against the same built `dist/index.js` (commit `e1a256bf9553bf9eb4bfcb935ce35cf090ac0291`, which includes `e38f90a`):

1. **Same-file edit, cold + warm** (`tmp/chg-reverify/cold/FalseGreen.agda`, `tmp/chg-reverify/warm/FalseGreen.agda`, driver `tmp/run-warm-false-green.mjs`): a self-contained module with `isZero : Nat → Bool` where the second clause is either well-typed (`= false`) or a genuine `UnequalTerms` mismatch (`= zero`). Cold: three fresh `dist/index.js` processes each loaded the already-broken file directly. Warm: one long-lived session loaded the well-typed content first, then the file was mutated **out-of-band** (raw `writeFileSync`, not via any MCP write tool) to the broken content, then `agda_load`/`agda_typecheck`/`agda_load_no_metas`/`agda_proof_status` were called in sequence against the same session.
2. **Two-file transitive, hard error in dependency** (`tmp/chg-reverify/transitive/{Main,Dep}.agda`, driver `tmp/run-transitive-staleness-repro.mjs`): `Main.agda` does `open import Dep; check = isZero zero`. `Main.agda` is loaded once (ok-complete), then only `Dep.agda` is mutated out-of-band to introduce the same `UnequalTerms` mismatch inside its own body, then `Main.agda` is reloaded in the same warm session — the canonical #64 trigger per CONCERNS.md ("edit a dependency module's source after its interface has been loaded into the long-running interactive session, then reload only the top-level file").
3. **Two-file transitive, signature-only change (dependency still typechecks cleanly on its own)** (`tmp/chg-reverify/transitive2/{Main,Dep}.agda`, driver `tmp/run-transitive-signature-repro.mjs`): `Dep.agda`'s `getValue` changes type from `Nat` to `Bool` — `Dep.agda` alone still compiles with **zero errors** (independently confirmed: `agda Dep.agda` on the changed content → `EXIT_CODE=0`) — only `Main.agda`'s `useValue : Nat; useValue = getValue` becomes ill-typed. This is the literal shape CONCERNS.md names for #64 ("a record turned into a type synonym... discharging via a pre-existing... interface"). Same warm-session reload pattern as (2).

Raw-`agda` ground truth was captured for every state (`tmp/chg-reverify/results/cold-raw-agda.txt`, `warm-raw-agda-before.txt`, `transitive-raw-agda-before.txt`, `transitive-raw-agda-after.txt`, `transitive2-raw-agda-before.txt`, `transitive2-raw-agda-after.txt`), always via `(cd <fixture-dir> && agda <basename>.agda; echo EXIT_CODE=$?)` — batch `agda` requires cwd = the file's own directory for its module-name/file-name check to pass.

**Observed (current main):** All three shapes show the SAME outcome — no false green.

- Cold, broken-from-the-start: `cold-agda_load.json` → `"classification": "type-error"`, `"data": {"success": false, ...}`. Raw `agda`: `EXIT_CODE=42` with `error: [UnequalTerms]\nNat !=< Bool`.
- Warm, same-file inject (`warm-false-green.json`): `initialLoad.classification = "ok-complete"`, `initialLoad.data.success = true`. After the out-of-band edit, `reloadAfterInject.agda_load` → `"ok": true, "classification": "type-error"`, `"data": {"success": false, "reloaded": true, "staleBeforeLoad": true, "previousClassification": "ok-complete", ...}`, with `diagnostics` including `{"severity": "info", "message": "Regression: this file loaded as ok-complete 0s ago. It may have been modified since, or a dependency may have changed.", "code": "session-regression"}`. `agda_typecheck` and `agda_load_no_metas` both independently return `"classification": "type-error"`, `"success": false`, quoting the same `UnequalTerms` error text.
- Two-file, hard error in `Dep.agda` (`transitive-staleness.json`): `initialLoad.classification = "ok-complete"`. After editing only `Dep.agda`, reloading `Main.agda` gives `reloadAfterInject.agda_load.classification = "type-error"`, `data.success = false`, `data.errors[0] = ".../Dep.agda:13.18-22: error: [UnequalTerms]\nNat !=< Bool\n..."`, plus the same `session-regression` diagnostic. Raw `agda Main.agda` after the swap: `EXIT_CODE=42` with the identical error text (`transitive-raw-agda-after.txt`); before the swap: `EXIT_CODE=0` (`transitive-raw-agda-before.txt`).
- Two-file, signature-only change in `Dep.agda` (`transitive-signature-staleness.json`): identical shape — `reloadAfterInject.agda_load.classification = "type-error"`, `data.errors[0] = ".../Main.agda:6.12-20: error: [UnequalTerms]\nBool !=< Nat\nwhen checking that the expression getValue has type Nat"`, `previousClassification: "ok-complete"`, `session-regression` diagnostic present. Raw `agda Main.agda` after the swap: `EXIT_CODE=42` with the matching error (`transitive2-raw-agda-after.txt`); `Dep.agda` alone independently verified to still compile with `EXIT_CODE=0`.
- **Related sub-finding (the "state-change tools reporting 'solved' after a failed reload" candidate):** `agda_proof_status`'s `data.text` in all three post-inject captures still ends with the literal string `"All goals solved.\n"` even though `data.hasConstraints: true` and `data.constraintsText` correctly quotes the real `UnequalTerms` error, and `data.goalCount: 0`. This is a genuine (minor) labeling inconsistency — the tool is technically correct in its structured fields (`hasConstraints`, `constraintsText`) but its human-readable summary text is misleading in isolation. It is NOT a full false green (the error is present and correctly surfaced in `constraintsText`), but it is exactly the kind of "state-change tools reporting solved" pattern CHG's context flagged, and it should be captured as its own smaller regression candidate.

**Implication:** changed → do not carry the flagship #64/#61 false-green forward into LOCK-03 as an "is currently reproducing" defect; none of the three constructed repro shapes reproduce it against `e1a256bf9553bf9eb4bfcb935ce35cf090ac0291`/`e38f90a`. However, treat this as **provisionally-fixed, not proven-fixed**: (a) `e38f90a`'s own commit message attributes the fix to a completion-detection idle-timer race that only manifests on a "large module" with a syntax-highlighting "compute gap" — my synthetic fixtures are tiny (6-8 lines) and load in well under a second, so they may never have entered the at-risk timing window that CHG's real agda-unimath-scale corpus hit; (b) `git show --stat e38f90a` confirms `src/agda/agdai-cache.ts` (the file CONCERNS.md names as the actual architectural gap — "forceRecompile only busts the named file's own `.agdai`") was **not modified** by that commit, so the theoretical per-file-not-transitive cache-bust gap likely still exists as *written code*, even though it did not manifest in any of my three practical repro attempts. LOCK-03's fixture should (1) start from one of these three repro shapes (the signature-only-change variant is the strongest, since it isolates true interface staleness from a body-level error), (2) additionally try a genuinely large/slow fixture or an explicit `forceRecompile: true` path to probe the timing-dependent and cache-architecture edges CONCERNS.md worries about, and (3) separately track the minor `agda_proof_status` "All goals solved." text mismatch as a low-priority Phase-4 queue item.

## Defect 2: `agda_auto` argument leak

**Verdict:** alive

**v0.6.7 claim:** Per `.planning/phases/01-capture-foundation/01-CONTEXT.md` deferred list: "`agda_auto` feeding `-d 5 --list-candidates` to Agda as an expression" — i.e. typed `hints`/`excludeHints` parameters are concatenated into a raw Agsy CLI-flag-shaped string with no escaping and sent as a literal expression to `Cmd_autoOne`.

**Repro:** `tmp/chg-reverify/auto-give/GoalOps.agda` (`trivial : Nat; trivial = {!!}`), driver `tmp/run-auto-give-repro.mjs`. After `agda_load` (goal ID `0` discovered from `data.goalIds[0]`, never hardcoded), a baseline `agda_auto` call with only `{goalId, writeToFile: false}` was made, then — because `agda_auto` was discovered during execution to close the goal in Agda's in-memory interactive state even with `writeToFile: false` (a deviation not documented in the plan's interfaces block: `Cmd_autoOne` gives internally on a found solution regardless of whether the MCP layer patches the on-disk file) — a fresh `agda_load` reopened goal `0` from the untouched on-disk file before the injection call: `agda_auto` with `{goalId, depth: 5, listCandidates: true, hints: ["-t 999999"], excludeHints: ["--unsafe"], writeToFile: false}`.

**Observed (current main):** `auto-give-repro.json` → `autoBaseline.data.searchPayload = ""` (empty, as expected with no flags). `autoWithFlags.data.searchPayload = "-d 5 --list-candidates -h -t 999999 -x --unsafe"` — the `hints` value `"-t 999999"` is concatenated verbatim after `-h ` and the `excludeHints` value `"--unsafe"` after `-x `, with **zero escaping or validation**, producing a string indistinguishable from a real extra CLI flag chain sent to Agsy. `autoWithFlags.ok = true`, `.classification = "ok"`, `.data.hasSolution = true`, but `.data.solution` is itself Agda's own rejection text (`"1.1-3: error: [NotInScope]\nNot in scope:\n  -d at 1.1-3\nwhen scope checking -d"`) — a bonus corroboration that the same "ok wrapping an error" pattern (Defect 3) also surfaces through `agda_auto`, not just `agda_give`.

**Implication:** alive → LOCK-03/Phase-4 queue candidate. `buildAutoSearchPayload()` (`src/agda/refactor-helpers.ts:112-131`, confirmed unmodified in this investigation) needs either strict escaping/validation of `hints`/`excludeHints` values or a documented "these are opaque search hints, not raw flags" contract with a warning diagnostic when a hint value looks flag-shaped (starts with `-`).

## Defect 3: `ok:true` wrapping Agda errors

**Verdict:** alive

**v0.6.7 claim:** Per `.planning/STATE.md` / `.planning/phases/01-capture-foundation/01-CONTEXT.md`: "`ok:true` wrapping Agda errors" — `agda_give` (and similar goal-text tools registered via `registerGoalTextTool`) always wrap the callback's return in `okEnvelope()` unless the callback throws; `session.goal.give()` does not throw on an Agda-level type-mismatch response, so a rejected `give` still reports `ok: true` at the envelope's top level while the rejection text is buried in `data.result`.

**Repro:** Same `tmp/chg-reverify/auto-give/GoalOps.agda` fixture and driver as Defect 2. After a fresh `agda_load` reopened goal `0`, `agda_give` was called with `{goalId, expr: "true", writeToFile: false}` — giving the `Bool` constructor `true` into the `Nat`-typed goal `trivial : Nat`, a direct, unambiguous type mismatch.

**Observed (current main):** `auto-give-repro.json.giveTypeMismatch` → top level `"ok": true, "classification": "ok"`. `data.result = "1.1-5: error: [UnequalTerms]\nBool !=< Nat\nwhen checking that the expression true has type Nat"` — Agda's own rejection message, stored as if it were a successful give's result text. `data.replacementText: null` confirms the give was in fact **not** applied (Agda rejected it), yet nothing at the envelope's `ok`/`classification` level distinguishes this from a genuinely accepted give. An agent branching only on `ok`/`classification` (the documented-fast-path contract per CLAUDE.md's `ToolInvocationError`/envelope conventions) would treat this as success.

**Implication:** alive → LOCK-03/Phase-4 queue candidate. `session.goal.give()` (`src/agda/goal-operations.ts:107-121`, confirmed unmodified) should either throw/return a distinguishable failure classification when the decoded response text matches Agda's own error-message shape (e.g. contains `error: [`), or `registerGoalTextTool` should inspect `replacementText === null` as a give-rejected signal and downgrade `classification` accordingly. This is the single highest-risk pattern for an agent silently committing a broken proof step.

## Defect 4: `agda_search_definitions` hardcoded `agda/` layout

**Verdict:** alive

**v0.6.7 claim:** Per `.planning/phases/01-capture-foundation/01-CONTEXT.md` deferred list: "`agda_search_definitions` hardcoding an `agda/` layout (dead on agda-unimath's `src/`)". Per the plan's interfaces block: the tool hardcodes its search root to `resolveFileWithinRoot(repoRoot, tier ? join("agda", tier) : "agda")`, i.e. it only ever looks under `<AGDA_MCP_ROOT>/agda/`, throwing `missingPathToolError("directory", ...)` if that directory doesn't exist.

**Repro:** Two byte-identical fixtures (`module Target where` + `data Nat` + `chgSearchTarget : Nat; chgSearchTarget = zero`) placed at `tmp/chg-reverify/layout-agda/agda/Target.agda` and `tmp/chg-reverify/layout-src/src/Target.agda` — the only difference is the containing directory name (`agda/` vs `src/`, mirroring agda-unimath's actual layout). `agda_search_definitions` was called with `{"query": "chgSearchTarget"}` against each project root via `scripts/mcp-local-client.mjs call-tool` (no loaded session required — the tool does not depend on prior `agda_load`).

**Observed (current main):**
- `search-definitions-agda-layout.json` → `"ok": true, "classification": "ok"`, `data.matchCount: 2`, `data.matches` listing both the type signature and the definition line under `agda/Target.agda`.
- `search-definitions-src-layout.json` → `"ok": false, "classification": "not-found"`, `data.text: ""`, `data.path` ending in `.../layout-src/agda` (note: **not** `.../layout-src/src`), and a diagnostic `"Directory not found: .../tmp/chg-reverify/layout-src/agda"` with `nextAction: "Confirm the directory exists relative to PROJECT_ROOT. Use \`agda_list_modules\` to enumerate available tiers and modules."` The identical `chgSearchTarget` content is completely invisible to the tool purely because it lives under `src/` instead of `agda/`.

**Implication:** alive → LOCK-03/Phase-4 queue candidate. `src/tools/file/search-definitions.ts`'s hardcoded `"agda"` tier root should either (a) fall back to scanning `PROJECT_ROOT` directly when no `agda/` subdirectory exists, or (b) read the search root from `.agda-mcp.json` project config (the existing per-project config mechanism), so agda-unimath-style `src/`-layout projects are not silently unsearchable.

## Methodology notes / deviations from the plan

- **`agda_auto` closes the goal in-session even with `writeToFile: false`** (discovered during Task 2, not documented in the plan's interfaces block): `autoOne()` (`src/agda/goal-operations.ts:179-191`) calls `ctx.syncGoalIdsFromResponses(responses)` after `Cmd_autoOne`, which reflects Agda's own interactive top-level state — Agda gives the found solution internally regardless of the MCP-layer `writeToFile` flag, which only controls whether the *file on disk* is patched. This meant the plan's literal 4-step driver script (baseline auto → flagged auto → give, all against one `agda_load`) would have failed at step 3 with `invalid-goal` because step 2 (baseline) already closed goal 0 in-session. Fixed by inserting a fresh `agda_load` (the on-disk file, untouched by `writeToFile: false`, still has the hole) before each subsequent probe that needs an open goal. This is a real, reproducible server behavior worth a footnote for anyone reusing `agda_auto` in future test design, but is not itself one of the 4 tracked CHG defects.
- **Batch `agda <file>` requires `cwd` = the file's own directory.** Running `agda /abs/path/to/File.agda` from an unrelated cwd fails with `[ModuleNameDoesntMatchFileName]` (Agda's module-name check resolves candidate files relative to its own working directory's discoverable include paths, not the directory containing the given file argument). All raw-`agda` ground-truth captures in this report use `(cd <fixture-dir> && agda <basename>.agda)`.
- **Defect 1 required going beyond the plan's literal single-file design** to reach a verdict consistent with "no verdict is guessed": the plan's Task 1 only specified a same-file edit-and-reload repro, but `.planning/codebase/CONCERNS.md` documents #64/#61 as specifically a *transitive dependency* staleness bug. Two additional two-file repro shapes (hard error in dependency; signature-only change in dependency) were added and independently cross-checked against raw-`agda` ground truth to test the actual documented bug mechanism, not just an adjacent same-file case. This is the deviation documented in the accompanying SUMMARY.md as a Rule-2 (missing critical functionality) addition to the investigation, not a plan change.
