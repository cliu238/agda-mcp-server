THE LOOP STAGES (Loop 2, shipped v1.0 2026-07-03, fed for real in v1.1 2026-07-05):
1. USE — an AI agent (Codex or Claude Code) does real Agda proof work through the MCP server, via the dogfood proxy (scripts/dogfood/dogfood-run.mjs) which records the session.
2. SURFACE — a defect or gap shows up during that session (a crash, a wrong result, or a suspicious "green").
3. CAPTURE — near-one-click structured capture: the agda_capture_session tool builds a self-replaying capture artifact plus a replay manifest, with stable fingerprints for dedup.
4. JUDGE — the oracle triad decides whether a "success" was real. A single cold re-run is NOT enough — each false-green family needs its own predicate:
   - ORCL-01 (cold-rerun differential): a fresh compile in a clean environment.
   - ORCL-02 (soundness scan): detects agent cheats — sneaky postulates, flag-planting, scope narrowing.
   - ORCL-03 (conformance proxy): checks whether the proved statement actually matches what was asked (the expectedSignature captured up front).
   Plus an N-times warm-replay anti-phantom gate so timing flakes never enter the queue as deterministic defects — a flaky result routes to a side channel instead of the fix queue.
5. FILE — a zod-validated flat-file fix queue with priority plus fingerprint dedup (dashboard: docs/FIX-QUEUE-DASHBOARD.md).
6. FIX+LOCK — each fix lands with a from-RED regression test: the test is written first against the bug, proven red, then the fix turns it green. The loop never golden-masters a false-green (never writes a test that just encodes the buggy behavior as "correct").
7. RE-USE — the hardened server goes back into the next proof session. The cycle compounds — each cycle makes the next session's server strictly stronger.

MOTIVATION (public-safe phrasing only — do NOT include private repo URLs): the loop's design is grounded in observed real agent behavior during the team's autoformalization campaigns — agents narrowing scope, taking shortcuts, planting flags to look done — not hypothetical failure modes. It is fine to NAME the two private fuel corpora (codex-homotopy-group, autoformalizing-hopf) since TEAM-ONBOARDING.md already names them; do not link to or describe their private repo URLs/contents beyond the name.

THE TEAM FEEDBACK CHANNEL (v1.1, live):
- Purpose: teammates' real proof sessions become loop fuel without the maintainer being in the room.
- Pipeline, in order:
  1. Maintainer issues a revocable Bearer key out of band (scripts/team/issue-key.mjs) — the server's registry stores only key HASHES, never the raw key; a consent statement is shared alongside the key telling the teammate exactly what an upload contains.
  2. Teammate does proof work through the dogfood proxy (records the session).
  3. dogfood-wrapup.mjs runs the oracle-triad judging locally, on the teammate's own machine.
  4. upload-run.mjs uploads the run archive. Upload is FAIL-OPEN with a bounded local retry queue — an unreachable ingest endpoint never blocks or corrupts the teammate's proof work; it just retries later.
  5. The ingest endpoint (https://dev.sites.idies.jhu.edu/agda-mcp/ingest) on the JHU IDIES k8s cluster receives it: streamed with a 512 MiB cap, archived by person/date onto durable Ceph PVC storage. Health check: https://dev.sites.idies.jhu.edu/agda-mcp/healthz.
  6. A daily sandboxed cron job on the cluster (cron-ingest-wrapup.mjs) re-judges uploads and files findings into the fix queue.
  7. Fixes get locked with regression tests; teammates pick up the hardened server by checking out the next v* tag.
- The cluster runs the exact same scripts as local — config-only differences. main auto-deploys on every push.
- Privacy/consent callout box (worth visually distinguishing, e.g. a bordered box): keys are revocable and stored only as hashes; the consent statement is shared with the key so the teammate knows exactly what an upload contains; uploads are archived per-person; no credential of any kind lives in the repo.
