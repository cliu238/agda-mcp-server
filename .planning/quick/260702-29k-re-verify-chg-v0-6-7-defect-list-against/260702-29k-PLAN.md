**`scripts/mcp-local-client.mjs` contract** (already read in full):
- `npx tsx scripts/mcp-local-client.mjs call-tool <toolName> '<jsonArgs>' [projectRootRelativeToRepoRoot]` — spawns a **fresh** `dist/index.js` server process per invocation (a genuinely cold session every time), calls the tool once, prints `JSON.stringify(result, null, 2)` to **stdout** (redirectable to a file), and prints server stderr separately to `console.error` (does not pollute redirected stdout).
- `[projectRootRelativeToRepoRoot]` sets `AGDA_MCP_ROOT` for that server process — this is the sandbox root every tool's file-path/search resolution uses.
- One invocation = one tool call = one process. It CANNOT be used to test "same warm session, multiple sequential calls" — for that, write a throwaway Node script using `createMcpHarness` directly (see below).

**`test/helpers/mcp-harness.ts`'s `createMcpHarness({ repoRoot, projectRoot })` contract** (already read in full):
- Returns `{ client, transport, listTools(), callTool(name, args), getServerVersion(), getServerCapabilities(), getStderr(), close() }`.
- `callTool(name, args)` returns the MCP SDK's `CallToolResult`: `{ content: [...], structuredContent: <ToolEnvelope>, isError }`. The `structuredContent` object is what to inspect — it has `{ tool, ok, classification, summary, data, diagnostics, stale?, provenance?, elapsedMs? }` (`src/tools/tool-envelope.ts`).
- One `createMcpHarness()` call = one spawned server process = one live session. Multiple sequential `callTool()` calls against the same harness instance are a genuinely warm/same-session sequence — this is the mechanism for the warm-session repro.
- Always `await harness.close()` in a `finally` block.
- A driver script placed at `tmp/<name>.mjs` (one directory below repo root, same depth as `scripts/`) can import `createMcpHarness` via the exact same relative specifier `scripts/mcp-local-client.mjs` uses: `../test/helpers/mcp-harness.js` (the `.js` specifier resolving to the sibling `.ts` file is handled by `tsx`, not by Node's resolver — this is why these scripts must run under `npx tsx`, never bare `node`).

**Envelope facts already established by reading source (do not re-derive):**
- `agda_load` / `agda_typecheck` (both drive `Cmd_load` under the hood; `agda_typecheck` is a slimmer-response variant of the same path) and `agda_load_no_metas` (`Cmd_load_no_metas`) each accept `{ file: string, ... }` and return `structuredContent.data.success`, `.data.classification` / top-level `.classification` (`ok-complete` / `ok-with-holes` / `type-error` / etc. — see `src/agda/session-load-helpers.ts` taxonomy), `.data.errors`, `.data.goalIds`. **Their top-level `ok` is unconditionally `true` on any non-throwing response** (`okEnvelope()` in `src/tools/tool-envelope.ts` hardcodes `ok: true`) — the real success/failure signal lives in `.classification` / `.data.success`, not `.ok`. This is a documented-by-design contract (CLAUDE.md: "a failed Agda load is an expected outcome, not an exceptional one"), but it is exactly the trap CHG's Skill warned against — record this distinction precisely in the report rather than conflating it with the flagship bug.
- `agda_proof_status` takes `{}` (no args), reads `session.getLoadedFile()`/`session.goal.metas()` from whatever is currently loaded in the session — it is only meaningful as part of a same-session sequence following a prior load.
- `agda_auto` (`src/tools/goal-tools.ts`, `Cmd_autoOne`) accepts typed `{ goalId, depth?, listCandidates?, hints?, excludeHints?, writeToFile? }`; internally `buildAutoSearchPayload()` (`src/agda/refactor-helpers.ts:112-131`) concatenates these into a raw Agsy CLI-flag-shaped string (e.g. `-d 5 --list-candidates -h <hint> -x <excluded>`) with **no escaping or validation** of hint/excludeHints values, then sends that literal string as the quoted third argument to `Cmd_autoOne`. The response always includes `data.searchPayload` — the exact constructed string — regardless of whether a solution was found.
- `agda_give` (`Cmd_give`) and friends (`agda_refine`, `agda_case_split`) are registered via `registerGoalTextTool` (`src/tools/tool-registration.ts`), which **always** wraps the callback's return value in `okEnvelope()` (`ok: true`, `classification` defaulting to the literal string `"ok"`) unless the callback throws. `session.goal.give()` (`src/agda/goal-operations.ts:107-121`) does not throw on an Agda-level type-mismatch response — it just returns `{ result: <decoded text, which may be an Agda error message>, replacementText }`. So a mistyped `agda_give` call returns `ok: true` + `classification: "ok"` at the envelope's top level while `data.result` embeds Agda's actual error text.
- `agda_search_definitions` (`src/tools/file/search-definitions.ts`) takes `{ query?, typePattern?, tier? }`, does **not** require a loaded session, and hardcodes its search root to `resolveFileWithinRoot(repoRoot, tier ? join("agda", tier) : "agda")` — i.e. it only ever looks under `<AGDA_MCP_ROOT>/agda/`. If that directory doesn't exist it throws `missingPathToolError("directory", ...)` (surfaces as an error envelope). A project using a `src/`-layout (like agda-unimath) is never found regardless of `query`.
