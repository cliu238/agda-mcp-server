# Phase 4: Triage / Fix Queue - Context

**Gathered:** 2026-07-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Deliver the **durable in-repo fix queue** that gives Loop ② backpressure before Phase-5 turns on the firehose:

1. an **in-repo flat-file queue** — the single source of truth for captured defects, fingerprint-keyed, with a status lifecycle, persisting across sessions (QUEUE-01),
2. a **prioritization signal** composed from already-captured data — false-green > crash > wrong-result > missing-feature, ties broken by recurrence (QUEUE-02),
3. the **`agda_triage_error` classifier wired in** — capture-time classification embedded in artifacts and class/kind carried on queue entries for routing (QUEUE-03; the tool itself already exists),
4. an **optional one-way GitHub Issues mirror** via `gh` — non-authoritative, the flat file stays SSOT (QUEUE-04).

**Not in this phase:** dogfooding orchestration + runbook (Phase 5), actually *fixing* the queue's cargo (ongoing post-scaffold work; Phase 3.1 owns the flagship #64/#61 fix), recurrence-weighted priority views (AUTO-03), agent-facing capture hints (AUTO-02), unattended intake/orchestration (AUTO-06), auto-PR (AUTO-05).

</domain>

<decisions>
## Implementation Decisions

> **Classification legend** (per the established Phase-1/2/3 convention):
> **[FORCED]** = fixed by correctness / a requirement / the phase boundary / an existing convention or charter — alternatives ruled out (reason given). Non-negotiable downstream.
> **[TASTE]** = a genuine values call the maintainer made.
> **[DEFERRED]** = deliberately unresolved (empirical or later-phase).
>
> This discussion surfaced exactly **four** taste decisions (D-03, D-05, D-07, D-13); everything else was forced by requirements, the Pitfall-6 research prescription, privacy correctness, or Phase-1/2/3 precedent. The user reviewed and approved the forced set as presented.

### Queue storage & SSOT (QUEUE-01)

- **D-01 [FORCED — codebase matrix-SSOT convention + programmatic consumers + "in-repo" requirement]:** The queue SSOT is a **machine-readable flat JSON file, git-tracked, inside the repo**. Scripts and agents must compose over it programmatically (design charter: compose-in-code), and the repo's established idiom is matrix-as-SSOT JSON + typed loader (`release-bug-matrix.json` / `fixture-matrix.json`). Markdown-as-SSOT is ruled out (bespoke parsing, drift). **It cannot live under `.agda-mcp/`** — that whole tree is gitignored, which would violate QUEUE-01's "in-repo" wording; a new tracked home is required (exact dir/name = Claude's discretion). JSONL vs single-JSON-array-with-typed-loader is plan-phase detail; lean on the existing loader idiom.
- **D-02 [FORCED — git-tracked file already IS the audit log]:** Status transitions **mutate the entry in place**; no append-only event log. Every transition of a tracked file is a commit — git history supplies the timestamped audit trail; a second event stream would be redundant machinery.
- **D-03 [TASTE — user decision]:** A **derived human-readable Markdown dashboard** (priority-sorted table + per-status counts + the close-rate metric) is regenerated by script whenever the queue changes. It is a *view*, never hand-edited (hand edits would drift from the SSOT). JSON remains the only truth.

### Dedup-index handoff (supersedes Phase-1 minimal index)

- **D-04 [FORCED — SSOT / split-brain + Phase-1 D-03 "superseded by the Phase-4 queue"]:** The Phase-1 minimal dedup index (`.agda-mcp/captures/index.json`) **retires**. CAP-02 dedup at capture time reads the **in-repo queue file** instead (`readDedupIndex()`'s read side repoints; emit-only constrains *writes*, reads are fine). Two files carrying recurrence counts would inevitably diverge. Bonus: recurrence history now survives clones/machine switches (the old index was machine-local). `promote-capture.mjs`'s write-side becomes/feeds the queue's intake write path (extend-vs-replace = plan-phase detail).

### Intake & first cargo (QUEUE-01/02 + Phase-3 D-10)

- **D-05 [TASTE — user decision]:** The **CHG first cargo (8 turn-key regression specs + 4 candidate defects — measured on v0.6.7, no capture artifacts) enters the queue immediately**, flagged **needs-reverify**. Re-verification against current `main` is a *triage action performed from inside the queue*; an entry that fails re-verification transitions to `rejected` (reason: cannot-reproduce / fixed-already). Ruled out: re-verify-before-entry — re-verification needs corpus setup and takes real time, during which the material would sit in exactly the untracked-evaporation state QUEUE-01 exists to kill.
- **D-06 [FORCED — Pitfall 6 prescription + QUEUE-01 persistence mandate]:** Graveyard guards from day one: **dedup bumps the existing entry** (never a second entry per fingerprint); a **WIP limit applies to the `fixing` status only and is advisory** (warning when exceeded) — a hard intake block would manufacture the evaporation QUEUE-01 forbids; a **close-rate/throughput metric is recorded from day one** and surfaced on the D-03 dashboard.

### Status lifecycle (QUEUE-01)

- **D-07 [TASTE — user decision]:** Status set = `new / triaged / fixing / locked` (the requirement's four) **plus a fifth terminal `rejected` with a reason field** (`not-a-bug | wont-fix | cannot-reproduce`). Without it, dead entries squat in `new` forever and corrupt the backlog signal; it is also the exit path for D-05 cargo that fails re-verification.
- **D-08 [FORCED — Phase-3 D-04 precedent / consistency]:** Status transitions are **manual-first** (a one-line file edit), helper scripts only if friction appears — the same philosophy the maintainer already chose for the Phase-3 red→locked matrix flip. The queue's `locked` corresponds to the regression matrix's `locked`; the exact linkage mechanics (manual vs emitter-assisted) are plan-phase detail.

### Classification axes (QUEUE-02/03)

- **D-09 [FORCED — the requirements themselves define two distinct taxonomies]:** **Two separate classification axes, never merged:**
  - *Agda-error machine class* — what Agda said: the **existing** `agda_triage_error` tool (`src/tools/agent-ux/edit-tools.ts` backed by `src/agda/error-classifier.ts`) already ships `mechanical-import / mechanical-rename / parser-regression / coverage-missing / proof-obligation / dep-failure / toolchain` + confidence + suggestedAction — covering QUEUE-03's named classes.
  - *Server-defect kind* — how the server misbehaved: `false-green > crash > wrong-result > missing-feature`, QUEUE-02's forced priority ordering (ties by recurrence).
  The CHG 12 anomaly families inform the *server-defect* axis and queue routing, not the Agda-error enum. Merging them would conflate "the proof has a coverage error" with "the server lied about the result".
- **D-10 [FORCED — QUEUE-03 wording "feeding both capture-time classification and fix-queue routing"]:** Phase 4's QUEUE-03 work is **wiring, not building**: embed the `TriageResult` into the capture artifact at capture time (modifying the existing Phase-1 `src/` capture addition is allowed per the Phase-2 precedent; no *new* `src/` surface), and carry class + defect-kind on queue entries. Priority is **composed from already-captured data**: ORCL-01 verdict (false-green candidates), capture `sessionClassification`, triage class, recurrence from the queue itself.

### GitHub mirror (QUEUE-04)

- **D-11 [FORCED — privacy correctness + charter P2]:** Mirror payload = **summary + fingerprint + class/kind + priority + status only — never inlined source, diffs, or capture-bundle contents.** Captures may contain private-corpus source (CHG / autoformalizing-hopf are access-gated) and this repo is public; full-bundle mirroring is a leak. One-way and non-authoritative per the requirement — the flat file stays SSOT.
- **D-12 [FORCED — one-way mirror correctness]:** The mirror is **idempotent**: each mirrored queue entry stores its GitHub issue number as a backlink; re-runs update the existing issue, never file duplicates.
- **D-13 [TASTE — user decision]:** Mirror scope = **only entries at status `triaged` or later** (human-reviewed before anything goes public). Raw `new` intake never auto-publishes. Whether `rejected` entries get *newly* mirrored (vs only updated when already public) = Claude's discretion.

### Claude's Discretion

- Queue file name + tracked location; JSONL vs single JSON + typed loader (follow the `release-bug-matrix` idiom); entry schema field names.
- Dashboard filename, layout, and regeneration trigger (same script that mutates vs standalone refresh).
- WIP-limit default value N (advisory threshold).
- How `needs-reverify` is represented (boolean flag vs annotation on `new`/`triaged`) — must not add a sixth status silently.
- Mirror labels/title conventions; `rejected`-entry mirroring nuance (D-13).
- How the Phase-3 emitter's locked flip reflects into the queue entry (manual vs script-assisted, per D-08).

</decisions>
