# Phase 03.1: Fix the #64/#61 transitive-staleness false-green and flip the flagship lock to green - Research

**Researched:** 2026-07-02
**Domain:** Agda `--interaction-json` transport completion-detection (IOTCM response-stream terminus signals); `Cmd_load_no_metas` protocol behavior
**Confidence:** HIGH — the central design question was resolved by building and empirically validating a full working prototype fix against real Agda 2.8.0 and the actually-built server (not just protocol-doc reading or theorizing), including a repeated, direct check of the D-02 false-RED risk and a full regression pass across the existing test suite.

## Summary

The central research question — "what is the correct `Cmd_load_no_metas`-appropriate terminus/completion signal?" — is answered empirically, not by extending the existing `awaitGoalTerminus` predicate but by recognizing it **cannot** be extended as-is. A raw IOTCM probe against local Agda 2.8.0 shows that a clean, hole-less `Cmd_load_no_metas` load emits `Status(checked=false)` → `ClearRunningInfo` → `ClearHighlighting` → highlighting payload, and then **nothing else, ever** (confirmed with an 8-second quiet window) — no second `Status`, no `InteractionPoints`, no `AllGoalsWarnings`. This directly disproves the natural first guess (mine, initially) that a trailing `Status(checked=true)` could serve as a no-metas success terminus: it does not exist. Every scenario that legitimately should fail — a genuine type error, a visible hole, and (importantly, tested across 11 varied fixtures including abstract-block/invisible-meta shapes) every unsolved-meta shape in the existing 72-entry fixture matrix — reliably emits `DisplayInfo`/`Error` at the protocol level. So `Cmd_load_no_metas` has exactly **one** positive event to await (failure), and **zero** for success; unlike the metas path, "no terminus observed" is the *normal* signature of success, not evidence of truncation.

The correct fix is therefore not "await a terminus, fail closed if absent" (that IS the D-02 trap) but **"widen the transport's idle-resolution window to the same long, configurable duration the metas path already uses (`AGDA_MCP_LOAD_TERMINUS_IDLE_MS`, default 2000ms), keyed on whether a `DisplayInfo Error` has been observed yet."** While unseen, every incoming response (highlighting, running-info, etc.) keeps re-arming the long window, so a real compute gap has time to surface a delayed error before the transport concludes "done." Once an error *is* seen, the transport reverts to the existing short windows, so failure cases stay fast (measured ~270–300ms, matching today). Only genuinely clean, error-free loads pay the new latency cost, because there is no way to shortcut waiting for "nothing more is coming."

I implemented this design as a prototype (`loadTerminusMode: "metas" | "strict" | null` generalizing the existing boolean `awaitGoalTerminus` field in `src/session/agda-transport.ts`, wired through `session.ts`/`session-command-dispatch.ts`, with `runLoadNoMetas` passing `{ loadTerminusMode: "strict" }`), built it, and validated it directly:
- The flagship `capture-regression.test.ts` entry flips from failing (`status:"red"`, asserts `matchesExpected===false`) to passing (`status:"locked"`, asserts `matchesExpected===true`) — exactly D-03's definition of done, reproduced live.
- The D-02 risk was checked explicitly and repeatedly: the SAME clean fixture, under the SAME extreme fault-injection env (`AGDA_MCP_IDLE_COMPLETION_MS=1`, `AGDA_MCP_POST_STATUS_IDLE_MS=1`) that triggers the false green on a broken edit, still correctly reports `ok-complete`/`success:true` — 3 repeated runs × 2 calls each, 6/6, taking ~2.0–2.3s instead of the near-instant (falsely green) resolution today.
- The metas path control (`agda_load`) and the full existing suite (1460 unit/property tests, 37 `agda-load.test.ts` integration tests, all 73 `agda-fixture-matrix.test.ts` strict-phase tests across all 72 existing fixtures including every hole/error/abstract-meta shape) all still pass — zero regressions.
- The measured cost is precise: the full 72-fixture strict-phase suite went from 81.04s (baseline/original code) to 131.89s (with the fix) — a ~51s (~63%) increase, entirely attributable to the ~27 genuinely-clean fixtures each now paying ~1.75–1.9s of added latency (270ms→2000ms+) that error/hole fixtures do not pay.

The prototype was reverted (via `git stash`/`git stash drop`) after validation so the repository is unchanged by this research session — the concrete diff shape below is a validated reference for the planner, not a merged change.

**Primary recommendation:** Generalize `AgdaTransport`'s existing `awaitGoalTerminus` boolean into a `loadTerminusMode: "metas" | "strict" | null` field. In `"strict"` mode, `sawGoalTerminus()` returns `sawLoadError` only (never gated on `InteractionPoints`/`AllGoalsWarnings`, which a clean strict load never emits). `runLoadNoMetas` passes `{ loadTerminusMode: "strict" }` to `sendCommand` and otherwise requires **zero** other code changes — `parse-load-responses.ts` and `session-load-helpers.ts`'s classification logic are untouched, and no new classification string is needed. Reuse the existing `AGDA_MCP_LOAD_TERMINUS_IDLE_MS` env var for both paths (same underlying physical phenomenon — Agda's real compute time — justifies the same tolerance). Because this pushes the already-oversized `src/session/agda-transport.ts` (535 lines, a documented existing outlier) further over the 500-line ceiling, extract the terminus-tracking state/methods into a new sibling module before or as part of this change.

### Pattern 1: Generalize a boolean gate into a small mode enum (the validated fix)

**What:** `AgdaTransport`'s existing `private awaitGoalTerminus = false` field and `options: { awaitGoalTerminus?: boolean }` parameter generalize into `private loadTerminusMode: "metas" | "strict" | null = null` and `options: { awaitGoalTerminus?: boolean; loadTerminusMode?: "metas" | "strict" | null }` (the old option name stays supported for backward compatibility — `runLoad`'s existing `{ awaitGoalTerminus: true }` call needs no change and still selects `"metas"` mode).
**When to use:** Exactly this situation — two call sites need "wait longer before resolving on idle," but disagree on WHAT confirms "done."
**Validated diff (prototype, built + tested against real Agda 2.8.0, then reverted):**

```typescript
// src/session/agda-transport.ts — the core of the fix

type LoadTerminusMode = "metas" | "strict" | null;

export class AgdaTransport {
  // ...
  private loadTerminusMode: LoadTerminusMode = null;
  private sawInteractionPoints = false;
  private sawAllGoalsWarnings = false;
  private sawLoadError = false;

  sendCommand(
    proc: ChildProcess,
    command: string,
    timeoutMs = configuredCommandTimeoutMs(),
    options: { awaitGoalTerminus?: boolean; loadTerminusMode?: LoadTerminusMode } = {},
  ): Promise<AgdaResponse[]> {
    // ...
    this.loadTerminusMode =
      options.loadTerminusMode ?? (options.awaitGoalTerminus ? "metas" : null);
    // ... rest of the existing reset logic, unchanged ...
  }

  private recordGoalTerminusResponse(response: AgdaResponse): void {
    if (!this.loadTerminusMode) return;
    if (response.kind === "InteractionPoints") {
      this.sawInteractionPoints = true;
    } else if (response.kind === "DisplayInfo") {
      const infoKind = (response.info as { kind?: unknown } | undefined)?.kind;
      if (infoKind === "AllGoalsWarnings") this.sawAllGoalsWarnings = true;
      else if (infoKind === "Error") this.sawLoadError = true;
    }
  }

  // THE key change: mode-dependent predicate.
  private sawGoalTerminus(): boolean {
    if (this.loadTerminusMode === "strict") {
      return this.sawLoadError; // no positive success event exists to await
    }
    return this.sawLoadError || (this.sawInteractionPoints && this.sawAllGoalsWarnings);
  }

  // bumpIdleCompletionTimer()'s two call sites pass
  // `awaitGoalTerminus: this.loadTerminusMode !== null` — command-completion.ts
  // itself needs ZERO changes, since it only ever consumed opaque booleans.
}
```

### Pattern 2: Extract before the file grows past the ceiling (REQUIRED, not optional)

**What:** `src/session/agda-transport.ts` is already 535 lines — a CLAUDE.md-documented existing outlier ("treat as a known outlier, not a template for new files"). The Pattern-1 diff above adds ~46 net lines in place, landing at ~581. Per this project's own "barrel + focused siblings" convention (used elsewhere for `agent-ux.ts`, `apply-proof-edit.ts`, `agent-ux-tools.ts`), extract the terminus-tracking state and its three methods (`recordGoalTerminusResponse`, `sawGoalTerminus`, and the mode field itself) into a new sibling, e.g. `src/session/load-terminus-tracker.ts`.
**When to use:** As part of this fix, not as a follow-up — implementing Pattern 1 in place would make an already-flagged oversized file worse, which directly conflicts with D-05's "honor the 500-line ceiling."
**Suggested shape (not yet built/tested — a design sketch only, unlike Pattern 1 above):**
```typescript
// src/session/load-terminus-tracker.ts (NEW, sketch)
export type LoadTerminusMode = "metas" | "strict" | null;

export interface LoadTerminusState {
  mode: LoadTerminusMode;
  sawInteractionPoints: boolean;
  sawAllGoalsWarnings: boolean;
  sawLoadError: boolean;
}

export function createLoadTerminusState(mode: LoadTerminusMode): LoadTerminusState {
  return { mode, sawInteractionPoints: false, sawAllGoalsWarnings: false, sawLoadError: false };
}

export function recordLoadTerminusResponse(state: LoadTerminusState, response: AgdaResponse): void {
  if (!state.mode) return;
  if (response.kind === "InteractionPoints") state.sawInteractionPoints = true;
  else if (response.kind === "DisplayInfo") {
    const infoKind = (response.info as { kind?: unknown } | undefined)?.kind;
    if (infoKind === "AllGoalsWarnings") state.sawAllGoalsWarnings = true;
    else if (infoKind === "Error") state.sawLoadError = true;
  }
}

export function isLoadTerminusSatisfied(state: LoadTerminusState): boolean {
  if (state.mode === "strict") return state.sawLoadError;
  return state.sawLoadError || (state.sawInteractionPoints && state.sawAllGoalsWarnings);
}
```
`AgdaTransport` then holds one `private terminus: LoadTerminusState` field, replacing the four scattered private fields, and delegates. This both shrinks `agda-transport.ts` (net negative line count vs. today, not just vs. the Pattern-1-in-place prototype) and produces an isolated, directly-unit-testable module (`test/unit/session/load-terminus-tracker.test.ts`) without needing a full `AgdaTransport`/child-process fixture.

## Common Pitfalls

### Pitfall 1: Assuming a trailing `Status(checked=true)` exists for `Cmd_load_no_metas` success (my own first hypothesis — empirically disproven)
**What goes wrong:** Designing the fix around "wait for `Status` with `checked:true`" as the no-metas success terminus.
**Why it happens:** The official protocol notes doc (`tooling/protocol/data/official-cross-version-notes.json`'s `notmetasNote`) says a clean strict load emits "only highlighting + Status," which reads as if a confirming Status exists. It does not — that phrase refers to the *initial* `Status(checked=false)` every load (metas or strict) emits at the very start, not a trailing confirmation.
**How to avoid:** I directly probed a genuinely clean, import-free, hole-free file (`Clean.agda`) via raw IOTCM with an 8-second quiet window: the exact, complete sequence is `Status(checked=false)` → `ClearRunningInfo` → `ClearHighlighting` → highlighting payload lines, then **nothing** — confirmed twice with two independent probe scripts.
**Warning signs:** A design or test that waits for a second `Status` event on the no-metas path will hang until the whole-command timeout (120s default) on every clean load.

### Pitfall 2: Assuming holes/unsolved-metas surface via `InteractionPoints` under `Cmd_load_no_metas` (they don't — they surface as `DisplayInfo/Error`)
**What goes wrong:** Designing the "hole detected" branch of the fix around waiting for `InteractionPoints`, mirroring the metas path.
**Why it happens:** The metas path's success terminus IS `InteractionPoints` + `AllGoalsWarnings`; it's natural to assume the strict path's "goals remain" case works the same way, just without `AllGoalsWarnings`.
**How to avoid:** Empirically, `Cmd_load_no_metas` treats ANY remaining unsolved meta (visible hole, invisible/abstract meta, mixed visible+invisible) as a genuine `DisplayInfo`/`Error` at the protocol level — confirmed directly on a synthetic `WithHole.agda` probe AND across all 45 non-clean entries of the existing 72-fixture matrix (`WithHoles`, `AbstractHoleMultiple`, `NestedAbstractHole`, `MixedVisibleInvisible`, `MutualHole`, etc. — all resolved via the fast ~270–300ms path with the correct `type-error` classification). This is good news: the SAME `sawLoadError` predicate that catches genuine type errors also catches every "goals remain" case, with no extra logic needed.
**Warning signs:** A test asserting `InteractionPoints` presence for a no-metas hole case will find it absent (or empty) and may misdiagnose the fix as broken when it is not.

### Pitfall 3: The added latency is real, material, and asymmetric — surprising if not measured
**What goes wrong:** Assuming the fix is "free" because it only changes timing, not correctness logic.
**Why it happens:** The diff itself is small (~50 lines), which can read as low-cost.
**How to avoid:** I measured it precisely: every genuinely clean/goal-less strict load now takes ~2.0–2.3s (up from ~250ms) because there is no way to shortcut "wait long enough that a would-be error had its chance to appear." Failure-path loads (any error or remaining hole) are essentially unaffected (~270–300ms, same as today) because `sawLoadError` flips fast. Across the full 72-entry fixture matrix's strict phase, total suite time went from 81.04s to 131.89s (+~51s, +63%) — entirely attributable to the ~27 clean fixtures. Flag this prominently to whoever reviews/accepts the fix; it is an intentional, disclosed tradeoff, not an oversight.
**Warning signs:** CI duration creeping up specifically on `RUN_AGDA_INTEGRATION=1` runs; a reviewer surprised that "just a timing fix" made things visibly slower.

### Pitfall 4: The metas-path control's exact fail-closed classification is not perfectly deterministic under extreme (1ms) fault injection — this is pre-existing, not a regression
**What goes wrong:** Seeing `agda_load`'s control check report `type-error` in one run and (per Phase 3's own report) `load-incomplete-no-terminus` in another, and concluding the fix broke something.
**Why it happens:** Under `AGDA_MCP_IDLE_COMPLETION_MS=1`/`AGDA_MCP_POST_STATUS_IDLE_MS=1` — an intentionally extreme fault injection — the exact race outcome for the (untouched) metas path can depend on OS scheduling jitter. I observed `type-error` consistently (5/5) this session; Phase 3's own research reported `load-incomplete-no-terminus`. Both are fail-closed (`success:false`), never a false green.
**How to avoid:** Don't assert on the EXACT classification string for the metas-path control under this specific extreme env; assert only `success === false` (or reuse the existing, broader `agda-load.test.ts`/`agda-fixture-matrix.test.ts` suites — which run under DEFAULT timing and are fully deterministic — as the authoritative metas-path regression signal, which is what this research did: 37/37 and 73/73 passing).
**Warning signs:** A newly-added test asserting the metas path's EXACT classification string under the extreme fault-injection env may be flaky through no fault of this phase's fix.

### Pitfall 5: This fix does NOT close a process-crash-during-load gap — a disclosed, out-of-scope residual limitation
**What goes wrong:** Assuming the fix makes `runLoadNoMetas` fully "fail-closed" in the same total sense `runLoad` is.
**Why it happens:** `runLoad`'s `!parsed.sawLoadTerminus → loadIncompleteNoTerminus` check operates on the FINAL response array regardless of *how* the promise resolved (idle vs. process-close), so it incidentally also catches "Agda's process died mid-load" (a truncated stream for a totally different reason than idle-timing). This fix's widened-idle-window mechanism only governs *idle-triggered* resolution — `AgdaTransport.handleProcessClose()` resolves immediately (via `trailingResponseDelay`'s `origin === "process-close"` branch, which returns 0) regardless of `loadTerminusMode`, exactly as today.
**How to avoid:** This is a genuinely different failure mode (process crash) than the one FIX-01 targets (idle-timing truncation, the diagnosed #64/#61 mechanism) and reproducing/fixing it would require exposing the resolution `origin` to `runLoadNoMetas` — a larger API change than D-04's scope fence ("do not rewrite the idle-timeout heuristic broadly") sanctions. Flag it as an explicit, disclosed known-limitation in the plan/summary rather than silently scoping it in or pretending it's covered.
**Warning signs:** None expected within this phase's own test scenarios (the flagship and guard test are both idle-timing scenarios, not process-crash scenarios) — this is a forward-looking disclosure, not a currently-failing case.
