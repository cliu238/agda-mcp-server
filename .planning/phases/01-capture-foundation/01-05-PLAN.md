    manifest's `agdaDirContents`, never inlined) - this script does not attempt
    to reconstruct AGDA_DIR/library registration; scope this script strictly to

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| scripts/promote-capture.mjs CLI arg -> filesystem write | Path is operator-supplied (maintainer running the script by hand), not agent/MCP-caller-controlled - lower trust requirement than the in-server tool paths |
| scripts/verify-cold-replay.mjs -> cold agda subprocess | Spawns a disposable subprocess using the artifact's own pinned binary path; a malicious artifact could point agdaBinaryPath at an arbitrary executable |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-05-01 | Elevation of Privilege | verify-cold-replay.mjs spawning manifest.agdaBinaryPath | accept | This script is an explicit manual-verification tool run by the maintainer against their own staged artifacts (VALIDATION.md: "Manual-Only Verifications"), not an MCP-exposed capability an untrusted agent can trigger remotely - same trust level as running any local dev script |
| T-05-02 | Tampering | promote-capture.mjs index.json write | mitigate | Plain writeFileSync is acceptable here (documented rationale in Task 2's action: single-writer, out-of-band, operator-run script, not a concurrent MCP hot path) — but the script still validates the artifact JSON parses before writing anything, refusing malformed input rather than corrupting the index |
| T-05-03 | Information Disclosure | drainRecordedActions() surfacing prior tool args in the staged artifact | accept | This is CAP-04's entire purpose (a faithful action log) - the artifact is staged out-of-repo under .agda-mcp/captures/, same trust boundary as the rest of the CaptureArtifact, not returned to the MCP caller in full (Plan 01-01's CaptureReference stays reference-only) |

</threat_model>
