<objective>
## Phase Goal

**As a** maintainer (and the AI agents dogfooding this server), **I want to** have every captured defect persist, flow, and get prioritized/classified inside a durable in-repo queue, **so that** intake neither evaporates at session end nor outpaces fix throughput into a write-only graveyard.

*(Same phase-level user story as 04-01 — see that plan's objective for the full MVP_MODE adaptation note. This plan is the QUEUE-04 slice: after it lands, the queue CAN optionally publish a non-authoritative summary to GitHub Issues — but nothing does so automatically, and nothing in this plan's own verification ever touches a real GitHub repo.)*

Build the one-way, optional, non-authoritative GitHub Issues mirror mechanism. This is the phase's single genuinely security-relevant deliverable: it shells out to an external CLI (`gh`), so every invocation must use argv-array `execFileSync` (never `execSync`/shell-string interpolation) to prevent argument injection from queue-entry text fields, and the mirror must never be mistaken for authoritative status (the flat file is always the source of truth). Critically, it ships **dry-run by default** — building the capability (idempotent one-way upsert keyed by fingerprint; recognizes and updates pre-existing issue numbers like the flagship's already-open #64/#61, never blindly creating duplicates) without ever pushing to, creating, or closing a real GitHub issue unless a human explicitly passes `--execute`.

Purpose: RESEARCH.md found #64/#61 already open on GitHub RIGHT NOW despite the underlying regression being `locked` — a live, present-tense instance of the exact mirror-staleness risk this plan must not reproduce, and a live demonstration of why "update, don't blindly create" matters from day one.
Output: `scripts/queue/mirror-github.mjs` and a fully mocked/dry-run test suite proving the safety and correctness properties above — no live `gh` call anywhere in this plan's own verification.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Queue-entry text fields -> gh subprocess argv | `title`/`summary` (maintainer/agent-authored, but not fully trusted as shell-safe) become `execFileSync` arguments — must never be interpreted by a shell. |
| This repo's mirror -> public GitHub issue tracker | Outbound-only, one-way, non-authoritative; the mirror must never read issue state back to influence local status. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04-01 | Tampering | scripts/queue/mirror-github.mjs execFileSync calls | mitigate | Argv-array `execFileSync` with `shell: false` for every `gh` invocation (never `execSync`/a shell string) — a `title`/`summary`/`notes` value containing shell metacharacters cannot break out of its argument position (CWE-78), matching `src/index.ts`'s established convention verbatim. |
| T-04-04-02 | Information Disclosure | buildMirrorPayload | mitigate | Fixed field whitelist (`title`/`summary`/`fingerprint`/`defectKind`/`triageClass`/`status` only) — `capturePath`/`verdictPath`/`notes`/source/diffs are never read into the payload, preventing a private-corpus (CHG / autoformalizing-hopf are access-gated) source leak into this public repo's issue tracker (D-11). |
| T-04-04-03 | Repudiation | GitHub issue state vs. local queue status | accept | The mirror is strictly one-way (repo file -> GitHub); `mirrorEntry` never reads issue state back to decide local status; the flat file remains the single source of truth regardless of what happens to the mirrored issue on GitHub afterward. |
| T-04-04-04 | Elevation of Privilege | an automated/CI run accidentally publishing to the real repo | mitigate | `options.execute` defaults to `false` and the CLI requires the literal `--execute` flag; the dry-run path never calls `execFileSync` even once — proven by an automated, mocked test (Task 2, assertion 1) — so no autonomous or CI invocation of this script can mutate GitHub without an explicit, human-supplied flag. |
| T-04-04-SC | Tampering | `gh` CLI (external binary, not an npm/pip/cargo package) | accept | Not a package-manager install — the Package Legitimacy Gate does not apply. `gh`'s presence/auth is probed defensively via `isGhAvailable`; absence degrades to a graceful skip, never a hard dependency or a thrown error. |

</threat_model>
