<objective>
## Phase Goal

**As a** maintainer (and the AI agents dogfooding this server), **I want to** have every captured defect persist, flow, and get prioritized/classified inside a durable in-repo queue, **so that** intake neither evaporates at session end nor outpaces fix throughput into a write-only graveyard.

*(Same phase-level user story as 04-01 — see that plan's objective for the full MVP_MODE adaptation note. This plan is the QUEUE-04 slice: after it lands, the queue CAN optionally publish a non-authoritative summary to GitHub Issues — but nothing does so automatically, and nothing in this plan's own verification ever touches a real GitHub repo.)*

Build the one-way, optional, non-authoritative GitHub Issues mirror mechanism. This is the phase's single genuinely security-relevant deliverable: it shells out to an external CLI (`gh`), so every invocation must use argv-array `execFileSync` (never `execSync`/shell-string interpolation) to prevent argument injection from queue-entry text fields, and the mirror must never be mistaken for authoritative status (the flat file is always the source of truth). Critically, it ships **dry-run by default** — building the capability (idempotent one-way upsert keyed by fingerprint; recognizes and updates pre-existing issue numbers like the flagship's already-open #64/#61, never blindly creating duplicates; and on a real `--execute` run, persists its own created/newly-linked issue number back onto the entry so a second run never re-creates it) without ever pushing to, creating, or closing a real GitHub issue unless a human explicitly passes `--execute`.

Purpose: RESEARCH.md found #64/#61 already open on GitHub RIGHT NOW despite the underlying regression being `locked` — a live, present-tense instance of the exact mirror-staleness risk this plan must not reproduce, and a live demonstration of why "update, don't blindly create" matters from day one.
Output: `scripts/queue/mirror-github.mjs` (including the D-12 backlink-persistence step) and a fully mocked/dry-run test suite proving the safety and correctness properties above, including multi-run idempotency — no live `gh` call anywhere in this plan's own verification.
</objective>
