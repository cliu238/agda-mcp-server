## User Constraints (from CONTEXT.md)

### Locked Decisions

> **Classification legend** (per the established Phase-1/2/3 convention):
> **[FORCED]** = fixed by correctness / a requirement / the phase boundary / an existing convention or charter — alternatives ruled out (reason given). Non-negotiable downstream.
> **[TASTE]** = a genuine values call the maintainer made.
> **[DEFERRED]** = deliberately unresolved (empirical or later-phase).

**Queue storage & SSOT (QUEUE-01)**
- **D-01 [FORCED]:** The queue SSOT is a **machine-readable flat JSON file, git-tracked, inside the repo**. Scripts and agents must compose over it programmatically (design charter: compose-in-code), and the repo's established idiom is matrix-as-SSOT JSON + typed loader (`release-bug-matrix.json` / `fixture-matrix.json`). Markdown-as-SSOT is ruled out (bespoke parsing, drift). **It cannot live under `.agda-mcp/`** — that whole tree is gitignored, which would violate QUEUE-01's "in-repo" wording; a new tracked home is required (exact dir/name = Claude's discretion). JSONL vs single-JSON-array-with-typed-loader is plan-phase detail; lean on the existing loader idiom.
- **D-02 [FORCED]:** Status transitions **mutate the entry in place**; no append-only event log. Every transition of a tracked file is a commit — git history supplies the timestamped audit trail; a second event stream would be redundant machinery.
- **D-03 [TASTE]:** A **derived human-readable Markdown dashboard** (priority-sorted table + per-status counts + the close-rate metric) is regenerated by script whenever the queue changes. It is a *view*, never hand-edited (hand edits would drift from the SSOT). JSON remains the only truth.

**Dedup-index handoff (supersedes Phase-1 minimal index)**
- **D-04 [FORCED]:** The Phase-1 minimal dedup index (`.agda-mcp/captures/index.json`) **retires**. CAP-02 dedup at capture time reads the **in-repo queue file** instead (`readDedupIndex()`'s read side repoints; emit-only constrains *writes*, reads are fine). Two files carrying recurrence counts would inevitably diverge. Bonus: recurrence history now survives clones/machine switches (the old index was machine-local). `promote-capture.mjs`'s write-side becomes/feeds the queue's intake write path (extend-vs-replace = plan-phase detail).

**Intake & first cargo (QUEUE-01/02 + Phase-3 D-10)**
- **D-05 [TASTE]:** The **CHG first cargo (8 turn-key regression specs + 4 candidate defects — measured on v0.6.7, no capture artifacts) enters the queue immediately**, flagged **needs-reverify**. Re-verification against current `main` is a *triage action performed from inside the queue*; an entry that fails re-verification transitions to `rejected` (reason: cannot-reproduce / fixed-already). Ruled out: re-verify-before-entry — re-verification needs corpus setup and takes real time, during which the material would sit in exactly the untracked-evaporation state QUEUE-01 exists to kill.
- **D-06 [FORCED]:** Graveyard guards from day one: **dedup bumps the existing entry** (never a second entry per fingerprint); a **WIP limit applies to the `fixing` status only and is advisory** (warning when exceeded) — a hard intake block would manufacture the evaporation QUEUE-01 forbids; a **close-rate/throughput metric is recorded from day one** and surfaced on the D-03 dashboard.

**Status lifecycle (QUEUE-01)**
- **D-07 [TASTE]:** Status set = `new / triaged / fixing / locked` (the requirement's four) **plus a fifth terminal `rejected` with a reason field** (`not-a-bug | wont-fix | cannot-reproduce`). Without it, dead entries squat in `new` forever and corrupt the backlog signal; it is also the exit path for D-05 cargo that fails re-verification.
- **D-08 [FORCED]:** Status transitions are **manual-first** (a one-line file edit), helper scripts only if friction appears — the same philosophy the maintainer already chose for the Phase-3 red→locked matrix flip. The queue's `locked` corresponds to the regression matrix's `locked`; the exact linkage mechanics (manual vs emitter-assisted) are plan-phase detail.

**Classification axes (QUEUE-02/03)**
- **D-09 [FORCED]:** **Two separate classification axes, never merged:**
  - *Agda-error machine class* — what Agda said: the **existing** `agda_triage_error` tool (`src/tools/agent-ux/edit-tools.ts` backed by `src/agda/error-classifier.ts`) already ships `mechanical-import / mechanical-rename / parser-regression / coverage-missing / proof-obligation / dep-failure / toolchain` + confidence + suggestedAction — covering QUEUE-03's named classes.
  - *Server-defect kind* — how the server misbehaved: `false-green > crash > wrong-result > missing-feature`, QUEUE-02's forced priority ordering (ties by recurrence).
  The CHG 12 anomaly families inform the *server-defect* axis and queue routing, not the Agda-error enum. Merging them would conflate "the proof has a coverage error" with "the server lied about the result".
- **D-10 [FORCED]:** Phase 4's QUEUE-03 work is **wiring, not building**: embed the `TriageResult` into the capture artifact at capture time (modifying the existing Phase-1 `src/` capture addition is allowed per the Phase-2 precedent; no *new* `src/` surface), and carry class + defect-kind on queue entries. Priority is **composed from already-captured data**: ORCL-01 verdict (false-green candidates), capture `sessionClassification`, triage class, recurrence from the queue itself.

**GitHub mirror (QUEUE-04)**
- **D-11 [FORCED]:** Mirror payload = **summary + fingerprint + class/kind + priority + status only — never inlined source, diffs, or capture-bundle contents.** Captures may contain private-corpus source (CHG / autoformalizing-hopf are access-gated) and this repo is public; full-bundle mirroring is a leak. One-way and non-authoritative per the requirement — the flat file stays SSOT.
- **D-12 [FORCED]:** The mirror is **idempotent**: each mirrored queue entry stores its GitHub issue number as a backlink; re-runs update the existing issue, never file duplicates.
- **D-13 [TASTE]:** Mirror scope = **only entries at status `triaged` or later** (human-reviewed before anything goes public). Raw `new` intake never auto-publishes. Whether `rejected` entries get *newly* mirrored (vs only updated when already public) = Claude's discretion.

## Project Constraints (from CLAUDE.md)

These bind every Phase-4 design choice below; none of the recommendations in this document violate them.

- **Layering:** `protocol → agda → session → tools`; domain logic must stay out of `src/tools/*` (thin adapters only). Phase 4's only justified `src/` change (the `triage` field + its population) belongs in `src/agda/session-capture/*`, not in a tool file.
- **Single `AgdaSession` invariant** (issue #39): nothing in this phase spawns or requires a second session; queue scripts operate entirely offline over JSON files.
- **500-line file ceiling** in `src/`; oversized modules split into barrel + focused siblings. Any `src/` edit this phase makes must stay additive and small (a few new lines on `artifact-types.ts`, `dedup-index.ts`, `register-capture-session.ts`).
- **Command-builder SSOT:** not implicated — this phase never talks to the `agda` binary directly.
- **`ToolEnvelope` pattern:** not implicated — `agda_triage_error`'s tool contract is unchanged this phase (QUEUE-03 is wiring elsewhere, not a tool-surface change).
- **Static data tables live in JSON, loaded via a typed loader:** directly governs the queue file itself (D-01) — follow `loadValidatedJsonData()` + zod exactly as `capture-regression-matrix.ts` does.
- **No new dependency posture** (ROADMAP "Out of Scope": *"New logger / database / HTTP dependency... violates the existing Node builtins, no DB, no HTTP server posture"*): confirmed — `package.json` dependencies are only `@modelcontextprotocol/sdk` and `zod` `[VERIFIED: package.json]`. Phase 4 must ship with **zero new npm packages** (`gh` is an external CLI binary, not an npm dependency).
- **Security convention:** shell out via `execFileSync(cmd, argvArray)`, never `execSync`/string-built shell commands — already established at `src/index.ts:136-149` (explicit CWE-78 comment) and reused in `src/agda/session-capture/oracle-substrate.ts:49` (`execFileSync("git", [...])`) and `scripts/oracle/orcl-01-differential.mjs`. QUEUE-04's mirror script must follow this exactly for every `gh` invocation.
- **Vitest placement:** `test/unit/**`, `test/integration/**` per `vitest.config.ts`'s `include` globs; a `test/unit/queue/` directory is a natural, convention-following addition (parallel to `test/unit/agda/session-capture/`, `test/unit/reporting/`, `test/unit/fixtures/`).

## Summary

Phase 4 closes Loop ②'s backpressure gap. Phases 1-3.1 built capture, oracle judgment, and regression-locking, but every artifact they produce today either evaporates (staged captures under gitignored `.agda-mcp/captures/`) or lands in a narrow, single-purpose store (the regression matrix holds only **locked** entries). Nothing yet tracks "found but not yet fixed." This phase is close to 100% additive plumbing over already-existing pieces: it does **not** build a new classifier (`agda_triage_error` already ships), does **not** build a new oracle (Phase 2's verdict sidecar already emits the false-green signal QUEUE-02 needs), and does **not** touch the regression-lock mechanism (Phase 3 keeps owning `locked` regression tests). What it adds is: one new git-tracked JSON file (the queue) with a zod-validated typed loader following the exact idiom already used twice in this repo; a small set of `scripts/queue/*.mjs` (intake, priority scoring, dashboard regeneration, GitHub mirror) that read/write it; one small additive change to the existing Phase-1 capture path (`CaptureArtifact` gains a `triage` field, `readDedupIndex()` repoints its read side); and zero new npm dependencies.

Two things make this phase concrete rather than speculative, both verified directly in this research session rather than assumed. First, real seed material already exists and is already characterized: the flagship #64/#61 defect is `locked` in `test/fixtures/capture-regression-matrix.json`, but its corresponding GitHub issues #64 and #61 are **still open** (verified live via `gh issue view`) — a present-tense demonstration of the exact "mirror drifts from reality" failure QUEUE-04 must design against from day one, not as an afterthought. Second, `.planning/research/CHG-REVERIFY.md` (completed the same day as this phase's discuss-phase) already re-verified 3 of "the 4 CHG candidate defects" as still-`alive` against current `main`, with captured MCP-envelope evidence — these need translation into queue entries, not fresh repro work. Separately, this research pulled the actual content of the "8 CHG turn-key regression specs" from the private `emilyriehl/Codex-Homotopy-Group` repo (`gh repo clone`, read-only, sparse-checkout of `agda-mcp-ux-report/` only) — they are 8 prose UX-behavior specs, not yet Agda fixtures, and several overlap in root cause with the "4 candidates" (spec #4 IS the alive `agda_auto` flag-leak defect; spec #8 is the flagship's own family, and current `main` already partially addresses it). The planner should cross-reference, not double-enter.

**Primary recommendation:** Ship the queue as one new git-tracked JSON array (zod-validated typed loader, following the `capture-regression-matrix.ts` idiom exactly) plus `scripts/queue/*.mjs` for intake/priority/dashboard/mirror; make the only `src/` change an additive `triage` field on `CaptureArtifact` plus a repoint of `readDedupIndex()`'s read path; seed the queue at build time with 1 already-`locked` flagship entry (carrying its pre-existing GitHub issue numbers `[64, 61]`), 3 already-re-verified-alive CHG entries, 1 minor already-observed candidate, 1 Phase-3-surfaced symlink candidate, and up to 8 `needs-reverify` entries drawn from the CHG UX report — cross-referencing overlaps rather than duplicating.

## Architectural Responsibility Map

This project has no browser/frontend/CDN tier — it is a stdio MCP server plus an out-of-band scripts layer. Tiers below are this project's own established layers (per CLAUDE.md's Layers section), not the generic web-app 5-tier model.

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Queue SSOT persistence (read/write JSON) | Repo-tracked storage (new git-tracked file) | Scripts/orchestration | D-01: git-tracked flat file *is* the storage layer for this project (no DB); scripts are the only writers |
| Status lifecycle transitions (new→triaged→fixing→{locked\|rejected}) | Scripts/orchestration | Repo-tracked storage | D-08: manual-first one-line file edits; a helper script is optional polish, not required |
| Prioritization scoring (QUEUE-02) | Scripts/orchestration | — | Pure compute over already-captured data (verdict sidecar + recurrence); explicitly **not** a new `src/tools/*` surface (D-10) |
| Agda-error machine classification (QUEUE-03, `agda_triage_error`) | MCP tool surface (`src/tools/agent-ux/edit-tools.ts`) | Session/domain logic (`src/agda/error-classifier.ts`) | Already-shipped pure classifier + thin tool adapter; **unchanged this phase** |
| `TriageResult` embedding at capture time (D-10 wiring) | Session/domain logic (`src/agda/session-capture/*`) | MCP tool surface (`src/tools/register-capture-session.ts`) | Modifies the existing Phase-1 capture addition only; no new tool surface, per D-10 |
| CAP-02 dedup read-repoint to queue (D-04) | Session/domain logic (`src/agda/session-capture/dedup-index.ts`) | Repo-tracked storage | Read-only; capture stays emit-only (never writes the repo tree itself) |
| Dashboard regeneration (D-03) | Scripts/orchestration | Repo-tracked storage (output) | Derived view, never hand-edited; regenerated on every queue mutation |
| GitHub Issues mirror (QUEUE-04) | Scripts/orchestration | External service (GitHub via `gh`) | One-way, non-authoritative; shells out via `execFileSync`, never authoritative for status |

**Why this matters:** the biggest risk in this phase is architectural creep — reflexively reaching for a new `src/tools/*` surface (a "queue" MCP tool) when every requirement is satisfiable by scripts + a data file. QUEUE-03 already has its MCP tool; QUEUE-01/02/04 need none. The only legitimate `src/` touch is the narrow, additive Phase-1 capture-path change D-10 explicitly sanctions.

### Anti-Patterns to Avoid

- **A new `agda_fix_queue` MCP tool surface.** Nothing in QUEUE-01/02/04 requires a new tool; QUEUE-03's tool already exists. A queue-reading/writing tool would violate the "domain logic out of `src/tools/*`" layering and duplicate what a script already does more simply.
- **Merging the two classification axes** (D-09). `TriageClass` (Agda-error shape) and `defectKind` (server-misbehavior shape) answer different questions; a single merged enum would silently lose the false-green signal DESIGN-PRINCIPLES.md's guardrail explicitly protects.
- **An append-only event log alongside the queue file** (D-02). Git history already is the audit trail; a second log is redundant machinery this phase explicitly rejects.
- **Treating the GitHub mirror as authoritative** — e.g., reading issue state back to decide local status, or gating a `locked` transition on the issue being closed. QUEUE-04 is one-way and non-authoritative by requirement; the flat file never asks GitHub anything.
- **Using `octokit`/`node-fetch` for the mirror.** Adds a dependency for an optional feature the environment's already-authenticated `gh` CLI handles natively.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Stable content-addressed defect identity | A new hashing scheme | `fingerprintBugReport()` (`src/reporting/bug-report.ts`) — reuse verbatim | Already sha256-stable, sorted-key-normalized, and is the SAME function CAP-02/`agda_bug_report_bundle` already use; a second hashing scheme would produce fingerprints that can never match a live capture of the same bug |
| Crash-safe file writes | A custom write-then-rename routine | `writeFileAtomic()` (`src/session/safe-source-io.ts`) | Already handles same-directory temp file + `O_EXCL` + rename-on-success + cleanup-on-failure; used throughout `scripts/` for exactly this "repeatedly hand-run-and-updated JSON file" category |
| Path-traversal-safe file writes | Manual `..`-stripping / string checks | `resolveFileWithinRoot()` / `PathSandboxError` (`src/repo-root.ts`) | Already the sandboxing primitive `scripts/emit-regression.mjs` uses for the analogous "write into a tracked dir from artifact-derived input" operation |
| JSON schema validation + typed export | Hand-rolled `if (typeof x !== ...)` chains | `loadValidatedJsonData()` (`test/helpers/json-data.ts`) + zod | Exact existing idiom (`release-bug-matrix.ts`, `capture-regression-matrix.ts`, `fixture-matrix.ts`) |
| Shelling out to an external CLI | String-interpolated shell commands (`execSync`/`\`gh ...\``) | `execFileSync(cmd, argvArray)` | Established, security-commented convention (`src/index.ts`, `oracle-substrate.ts`) preventing CWE-78 command injection |

**Key insight:** every "don't hand-roll" item in this phase is a *reuse*, not a *library recommendation* — Phase 4's whole job is composing already-built, already-tested primitives from Phases 1-3 into one new data file and a handful of scripts. The only genuinely new logic is the priority-scoring function and the dashboard string-builder, both of which are simple enough (a 4-bucket categorical sort + a markdown-table join) that hand-rolling them is the *correct* choice, not a shortcut.

## Common Pitfalls

### Pitfall 1: Write-only graveyard (Pitfall 6, `.planning/research/PITFALLS.md`)
**What goes wrong:** Capture is frictionless; nothing pulls from the queue; duplicates aren't merged; the queue's signal-to-noise collapses.
**Why it happens:** Capture is automatable and satisfying; triage/fixing is human, slow, unglamorous.
**How to avoid:** Exactly D-06's prescription — dedup bumps the existing entry (never a second one per fingerprint), an advisory WIP limit on `fixing`, and a close-rate metric recorded from day one on the dashboard.
**Warning signs:** Queue length monotonically increasing; same defect under multiple fingerprints; items older than the milestone with no owner.

### Pitfall 2: The mirror silently drifts from local truth — ALREADY OBSERVED, not hypothetical
**What goes wrong:** A locally `locked`/`rejected` entry's mirrored GitHub issue is never updated to reflect that, so the public tracker shows stale state indefinitely.
**Why it happens:** D-12 only specifies *idempotent create-or-update on mirror* — it does not by itself specify *what triggers a re-mirror after the first one*.
**Evidence this is real, not theoretical:** `gh issue view 64/61` (verified live in this session) shows **both issues still OPEN**, even though `test/fixtures/capture-regression-matrix.json`'s `issue-64-61-transitive-staleness` entry has carried `"status": "locked"` since Phase 3.1 landed. Also notable: these are **pre-existing** issue numbers (`issue: [64, 61]`, an array — matching `capture-regression-matrix.ts`'s own `z.array(z.number())` schema for `issue`), not ones the (not-yet-built) mirror created — so the flagship's first mirror action is an *update-and-likely-close* of two already-public issues, not a *create*.
**How to avoid:** Recommend the mirror script re-runs (and updates/closes) on every local status change for any entry that has ever been mirrored, not only on first publish; treat pre-existing `issue[]` numbers (known before Phase 4 even ships) as already-linked, never re-created.
**Warning signs:** Any queue entry whose local `status` is terminal (`locked`/`rejected`) while its linked GitHub issue(s) remain open.

### Pitfall 3: Fingerprint fidelity depends on caller-supplied text, not just the hashing function
**What goes wrong:** Two captures of the *same* underlying defect can hash to *different* fingerprints, defeating CAP-02 dedup and QUEUE-02's recurrence tie-break.
**Why it happens (code-verified):** `register-capture-session.ts`'s current fingerprint call is:
```typescript
const fingerprint = fingerprintBugReport({
  kind: "new-bug",
  affectedTool: "agda_capture_session",   // ALWAYS this literal string, never the tool that actually failed
  classification: sessionClassification ?? "unknown",
  observed: inputs.note ?? "session capture",  // free-text agent note — varies session to session
  expected: "",
  reproduction: [],
  serverVersion: manifest.serverVersion,
});
```
`affectedTool` is hardcoded and `observed`/`expected`/`reproduction` are empty or free-text — unlike `agda_bug_report_bundle`'s call to the SAME function, which passes the real affected tool + real observed/expected content. This is a pre-existing Phase-1 characteristic, not something Phase 4 introduces, but QUEUE-02 leans directly on recurrence-as-tie-break, so its input signal has a known fidelity gap.
**How to avoid:** When hand-seeding queue entries with no live capture (the CHG cargo), compute the fingerprint with the SAME rich shape `agda_bug_report_bundle` uses (real `affectedTool`, a stable `observed`/`expected` drawn from the written evidence) rather than the weaker shape `agda_capture_session` currently produces — otherwise a *future* live re-capture of the exact same bug (e.g., during Phase 5 dogfooding) will not match the hand-seeded fingerprint and will wrongly appear as a brand-new defect instead of bumping recurrence.
**Warning signs:** The same bug appearing as two queue entries with different fingerprints after a live re-capture.

### Pitfall 4: Conflating the two classification axes (D-09)
**What goes wrong:** Someone tries to derive `defectKind` (false-green/crash/wrong-result/missing-feature) directly from `TriageClass` (mechanical-import/.../toolchain), or vice versa.
**Why it happens:** Both are "classify this defect" outputs, tempting a single mapping table.
**How to avoid:** They classify different things — one is about *what Agda said*, the other is about *how the server misbehaved*. A `toolchain`-class Agda error and a `false-green` server defect can co-occur or be unrelated. Keep them as two independent fields on the queue entry.

### Pitfall 5: Building status-transition tooling before friction is proven (Pitfall 7, PITFALLS.md)
**What goes wrong:** Building an interactive CLI/TUI for queue status edits, or a fully automated intake-to-mirror pipeline, before the manual one-line-edit process has been used enough to know it's actually painful.
**Why it happens:** Automation is the more interesting part of the work.
**How to avoid:** D-08 already forces manual-first; honor it literally — the planner should not add a `scripts/queue/set-status.mjs` helper unless the phase's own success criteria require it. Same for the WIP limit and close-rate metric: compute them, display them, but don't build enforcement machinery beyond an advisory warning.

### Priority scorer (QUEUE-02) — pure, deterministic
```javascript
// Recommended scripts/queue/priority.mjs shape
const DEFECT_KIND_WEIGHT = { "false-green": 0, "crash": 1, "wrong-result": 2, "missing-feature": 3 };

export function comparePriority(a, b) {
  const weightDiff = DEFECT_KIND_WEIGHT[a.defectKind] - DEFECT_KIND_WEIGHT[b.defectKind];
  if (weightDiff !== 0) return weightDiff;
  return b.recurrence - a.recurrence; // higher recurrence sorts first within the same defectKind band
}
```

### Shelling out to `gh` safely (QUEUE-04)
```javascript
// Source pattern: src/index.ts:136-149, src/agda/session-capture/oracle-substrate.ts:49
// (execFileSync, never execSync — CWE-78 command-injection prevention, already
// an established convention in this codebase)
import { execFileSync } from "node:child_process";

function createOrUpdateIssue(entry, bodyFilePath) {
  if (entry.githubIssue) {
    execFileSync("gh", ["issue", "edit", String(entry.githubIssue), "--body-file", bodyFilePath], { encoding: "utf8" });
    return entry.githubIssue;
  }
  const stdout = execFileSync(
    "gh", ["issue", "create", "--title", entry.title, "--body-file", bodyFilePath, "--label", "bug"],
    { encoding: "utf8" },
  );
  // `gh issue create` has NO --json flag (verified via `gh issue create --help`
  // in this session) — it prints the created issue's URL; parse the trailing number.
  const match = /\/issues\/(\d+)\s*$/.exec(stdout.trim());
  if (!match) throw new Error(`Could not parse issue number from gh output: ${stdout}`);
  return Number(match[1]);
}
```

## Security Domain

### Applicable ASVS Categories

> Verified against the **current** OWASP ASVS 5.0 structure via WebSearch in this session `[CITED: OWASP ASVS 5.0 official chapter list, owasp.org / github.com/OWASP/ASVS]` — ASVS 5.0 substantially renumbered categories relative to the older 4.x scheme (e.g. old "V2 Authentication" is not new "V2"). Using the stale 4.x numbering from training data would have been a real "deprecated features" trap; the table below uses the verified-current 5.0 chapter names.

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V1 Encoding and Sanitization | yes | `execFileSync(cmd, argvArray)` — never shell-string interpolation — for every `gh`/`git` invocation (CWE-78 prevention; already an established convention at `src/index.ts:136-149`) |
| V2 Validation and Business Logic | yes | zod-enforced queue-entry schema (enum-constrained `status`, refinement requiring `rejectedReason`/`closedAt` where applicable); status-lifecycle validity is itself a "business rule / state machine" concern this category is meant to cover |
| V3 Web Frontend Security | no | No browser frontend exists in this project |
| V4 API and Web Service | no (loosely covered by V2 at the MCP boundary) | This is a local stdio MCP server, not a REST/GraphQL web service; the closest-fit concerns (input validation at the tool boundary) are already covered under V2 and pre-date this phase |
| V5 File Handling | yes | `resolveFileWithinRoot()` / `PathSandboxError` (`src/repo-root.ts`) for every new queue/dashboard file write; `writeFileAtomic()` for corruption-safe writes |
| V6 Authentication | no | No authentication system exists in this codebase; `gh`'s own auth is external, pre-existing, and out of this codebase's control surface |
| V7 Session Management | no | `AgdaSession` is a domain object (interactive-proof state), not a security session |
| V8 Authorization | no | Single-user local CLI/MCP tool; no multi-tenant access-control model |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| OS command injection via `gh`/`git` argv built from queue-entry text (a `title`/`summary`/`note` containing shell metacharacters) | Tampering | `execFileSync(cmd, argvArray)` — never a shell string (established convention, `src/index.ts`, `oracle-substrate.ts`) |
| Private-corpus source/diff leak into the public GitHub mirror (CHG / autoformalizing-hopf captures may contain access-gated source; this repo's issue tracker is public) | Information Disclosure | D-11: mirror payload = summary + fingerprint + class/kind + priority + status **only**; the mirror's body composer must read a narrow field whitelist off the queue entry, never `CaptureArtifact.oracleSubstrate`/`recordedActions` |
| Path traversal when writing the queue/dashboard files from artifact-derived paths | Tampering | Reuse `resolveFileWithinRoot()`/`PathSandboxError` exactly as `scripts/emit-regression.mjs` already does for fixture writes |
| Mirror silently drifts from local truth (a GitHub issue's state is never reconciled after a local terminal-status transition) — **empirically observed already**, see Pitfall 2 | Repudiation (stale public status) | D-12's idempotent backlink, extended (recommended) so the mirror also updates/closes the linked issue on every local status change it mirrors, not only on first publish |
| The sha256 fingerprint mistaken for a security/integrity boundary | Spoofing (low-likelihood edge case) | It is a 16-hex-char (64-bit) truncated content-addressing hash for dedup only — never an auth token or tamper-evidence signal |
